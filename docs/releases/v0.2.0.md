AmuOSの2つ目のプレリリースです。この版では、運用の基盤を整えました。systemdのサービスとして常駐させられるようになり、停止中の暗号化バックアップと復元、再インストールせずに本体だけを入れ替える更新と、更新前のバックアップを使った切り戻しができます。まだ開発途中ですが、試していただいて気づいたことがあれば、Issueで教えていただけるととても助かります。

> [!WARNING]
> 開発途中のソフトウェアです。実機での長時間の運用や、独立した環境での復元の確認はまだ済んでいません。APIやデータ形式も予告なく変わることがあります。本番環境やインターネットに公開された環境での利用はお控えください。

## 新しくできること

- **systemdでの常駐**：配布物の `packaging/` に、サービスの設定ファイルを同梱しました。専用ユーザー `amuos` で動き、特別な権限は持たず、書き込めるのは `/var/lib/amuos` だけです。TLSの秘密鍵はrootだけが読める状態のまま使えます。サービスを止めても、止まるのはAmuOS自身だけです。
- **暗号化バックアップと復元**：サービスを止めてから、データベースの一貫した状態をage形式で暗号化して保存します。保存前に全体を読み戻して確かめます。復元は同じ版に限り、検証が済むまで今のデータベースには触れません。復元後は、ログイン中のセッションと未使用の招待が無効になります。詳しくは同梱の `BACKUP.md` をご覧ください。
- **更新と切り戻し**：`--check-db` で、新しい本体が今のデータベースを使えるかを、書き込みせずに確かめてから差し替えられます。問題があったときは、更新前のバックアップと、そのとき残しておいた本体の組で戻せます。
- **タスクの記録（API）**：ホストへの読み取り専用の作業（`collect`）を受け付けて記録する仕組みと、そのAPIを追加しました。ただ、作業を実行するAgentがまだないため、受け付けたタスクは60秒で期限切れになります。実際に動くのは、Agentを追加する次の版からです。
- 同じ状態ディレクトリを2つのプロセスが同時に使わないよう、起動時に排他ロックを取るようにしました。

## v0.1.x からの更新

データベースは起動時に新しい形式（スキーマv9）へ自動で移行されます。移行したあとに古い本体へ戻すことはできません。

v0.1.x にはバックアップのコマンドがないため、更新前の状態を取っておく手段がありません。申し訳ありませんが、v0.1.x からの更新は切り戻しの保証範囲に含まれません。大切なデータはまだ置かないでください。この版からは、同梱の `INSTALL.md` の「更新」の手順で、更新前にバックアップを取れます。

v0.1.x を手元のディレクトリで動かしていた場合、systemdのサービスへ移すときは、`INSTALL.md` の手順でサービスとして新しく導入してください。既存のデータベースを移す手順は、まだ用意できていません。

## まだできないこと

- Agentによるホスト情報の取得、監視とグラフ、タスクの実行
- AgentのCA再発行など、Agentに関わる復元後の信頼の作り直し（Agentとともに追加します）
- 自動バックアップのスケジュール、Webからの復元
- Linux amd64 以外向けの配布

## 確認した環境

- GitHub Actions の Ubuntu 24.04 で、この配布ファイルをsystemdのサービスとして導入し、専用ユーザーでの実行、ファイルの権限、再起動後のデータ保持、更新前のバックアップ、別の版への更新、更新前のバックアップを使った切り戻し、アンインストール後のデータ保持を確認しました。
- Ubuntu 24.04 と Debian 13 のコンテナで、手順どおりの手動導入、暗号化バックアップ、壊れたバックアップの拒否、復元を確認しました。
- Ubuntu 24.04 で取ったバックアップを、AmuOSを動かしたことのない Debian 13 のコンテナへ復元し、ログインとデータ・監査ログの保持を確認しました。
- 実機の Ubuntu Server や Debian での長時間の運用は、まだ確認していません。実際の形式移行を伴う版をまたいだ更新は、移行の自動テストで確かめています。

# アプリ登録（v0.7開発中）

仕様§8・§10・§16 Phase 4の最初の実装として、ホスト詳細画面でManaged Serviceのアプリ登録を管理する。現在の対象は登録名、予定するランタイム、アプリごとのロール設定である。デプロイ、プロセスの作成、起動・停止、依存取得、ログ・監視、シークレット、更新・切戻しは未実装で、v0.7の完了条件を満たしたものではない。

## 登録と認可

- 登録名はホスト内で一意。1〜63文字の英小文字・数字・ハイフンで、先頭は英小文字、末尾のハイフンは不可。名前は変更できない。
- 予定するランタイムは`python`・`node`・`binary`。実行環境が存在するかの検査やインストールは行わない。登録先が未接続でも登録できる。Linuxでの実行に向けたメタデータであり、Windows Agentで実行可能であることを意味しない。
- ホストを管理できるAdminと全体Ownerが登録・設定変更・登録解除を行う。Operator・Viewerには登録変更を許可しない。
- `read_roles`はAdmin・Operator・Viewerから指定する。ホストに適合する同じ割当のロールだけを照合する。AdminとOwnerは登録管理のため閲覧できる。別ホストのAdmin割当で、対象ホストのViewer割当を昇格させない。
- `operate_roles`は後続の操作認可に向けた予約設定で、現在は何も実行できない。Admin・Operatorだけを指定でき、`read_roles`の部分集合とする。画面からの新規登録では空配列とし、起動権限の設定UIは実行機能とともに追加する。
- 一覧は閲覧できる登録だけを返す。対象ホストの範囲外・アプリの閲覧対象外・登録解除済みの詳細は404。ポリシーと最新のユーザー割当を要求ごとに読み、無効ユーザーを拒否する。

ホストごとに有効な登録を128件、解除済みを含めて1,024件に制限する。登録解除済みの名前は再利用できない。実行機能追加後の停止・削除とは別の操作であり、現在の登録解除はホストのファイルやプロセスに触れない。

## 再送・競合・監査

リソースは`host_id/name`で決まる。PUTの`expected_revision:0`で作成し、既存の変更には読み取った`revision`を指定する。成功時に版を1増やす。別の内容に更新された古い版からの変更は409。

同じ入力を同じ期待版で再送し、現在の版が期待版+1で内容も一致すると、状態を変更せず現在の登録を返す。ロール配列の順序は無視する。同じ名前の異なる新規要求、解除済みの名前、新しい更新を挟んだ古い再送は409。登録解除の同じ期待版での再送も、解除後の版が期待版+1の場合だけ成功する。冪等キーを持つ実行タスクとは別の、登録情報に限った契約である。

登録、変更、解除と監査は同じDBトランザクションで確定する。成功監査は`application.put`・`application.archive`で、対象ホスト、登録名、変更前後の登録、実際に変更したかを記録する。拒否時は固定の理由だけを記録する。不明なJSONフィールド、コマンド、環境変数、秘密値の入力フィールドは受け付けない。

## 永続化と復元

スキーマ15で`applications`テーブルを追加する。v0.6のスキーマ14から移行するため、更新前に既存版でバックアップする。移行後のDBはv0.6のバイナリで開けない。切り戻す場合は更新前のバックアップと対応する版を使う。

登録と解除済みの記録は再起動後も保持する。管理基盤のバックアップのテーブル件数検証に含め、復元時も保持する。既存の復元処理に従って旧セッションは失効する。管理DBの復元によってプロセスを作成・開始する処理はない。将来のアプリ実データと秘密値の保護・復旧は、登録情報の復元と区別して設計する。

## 次の実装条件

高権限の実行Adapterを公開する前に、Linuxの専用実行ユーザー・作業領域・systemdとの境界、実行ファイルとランタイムの検証、秘密値の暗号化と投影、変更タスクの受付/配送/受領時認可、未知結果の照合、停止中断、更新と切戻しの契約をADR/APIに定める。Windows上のControl PlaneからLinux Agentへ指示する経路も検証する。登録情報だけの試験で実行・デプロイの成功を代替しない。

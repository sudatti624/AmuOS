# 停止中のバックアップと復元

現在のControl Planeの状態（ユーザー、範囲付きRBAC、ホスト登録、監査、保持設定、招待、冪等記録、タスク、Agentの登録・資格情報の記録、ホスト情報、監視履歴、systemdの状態）を、age v1/X25519で暗号化して保存します。同じ製品版・DBスキーマへの復元だけを受け付けます。`dev` は開発確認用であり、任意の異なるビルド間の互換性を保証しません。

v0.6ではファイルのルート権限設定と、タスクに保存された転送内容も含みます。ホスト側の実際の許可ディレクトリ、退避領域、Agentのローカルルート設定は含みません。それらは別途バックアップしてください。[FILES.md](FILES.md)も参照してください。スキーマ14へ移行するため、v0.5への切戻しには更新前のバックアップを使います。

バックアップ対象の永続状態はSQLiteです。アーカイブの `config.json` はコマンドで指定した `--addr` と `--origin` の確認用記録で、自動適用しません。バックアップ時には通常起動と同じ値を指定してください。TLS証明書・秘密鍵、OSのサービス設定、管理対象ホストのデータは含みません。復元先ではTLS証明書を別途用意し、接続先設定を確認します。

タスクの記録も含みます。復元したデータベースでは、受付待ちを含む未完了のタスクをすべて結果不明（unknown）として保留し、自動では配送・再実行しません。AgentのCAの証明書・秘密鍵は含めません。復元時には旧資格情報を失効させ、復元先の古いAgent CAを削除し、起動時に新しいCAを作成します。各Agentは新しいコードで再登録してください。監視履歴は復元対象ですが、管理対象ホスト上のAgentの状態ファイルやタスクジャーナルは対象外です。復号可能な保存シークレットはまだなく、`keys.json` は形式版1の空の鍵束です。未対応の鍵束やスキーマは拒否します。

## 復旧鍵の準備

OSの管理権限を持つ担当者が、保護された保存先で一度だけ生成します。以下のパスは環境に合わせて置き換えてください。親ディレクトリはあらかじめ0700で作り、復旧秘密鍵を本体・バックアップの保存先と別の障害領域へ保管します。

```sh
./amuos-controlplane --generate-recovery-key /protected-offline/amuos-recovery.key
```

標準出力には `age1...` の公開鍵だけを表示します。秘密鍵はLinuxでは新規0600ファイル、Windowsでは継承を無効にして作成者・SYSTEM・Administratorsに限定したファイルに書き込み、既存ファイルは上書きしません。age-keygenで作成した、X25519秘密鍵を1つ含むファイルも使用できます。秘密鍵をコマンド引数やチャットに貼り付けないでください。Linuxでは所有者以外にアクセス権のある復旧鍵を拒否します。外部ツールで作った鍵や移動・複製した鍵も、安全な権限で保管してください。

公開鍵を控えた後は、バックアップ時に秘密鍵を接続しておく必要はありません。秘密鍵を失うと復元できません。

## バックアップ

利用者のアクセスを止め、Control Planeを終了させてから、通常の実行ユーザーで実行します。サーバーと同じ状態ディレクトリの排他ロックを使うため、起動中は待機せず失敗します。

```sh
./amuos-controlplane --db /var/lib/amuos/amuos.db \
  --backup-out /protected-backups/amuos-2026-11-05.age \
  --recipient age1... \
  --addr 127.0.0.1:8443 --origin https://localhost:8443
```

出力の親ディレクトリは先に用意します。既存アーカイブは上書きしません。SQLiteバックアップAPIでWALのコミット済み状態を取得し、DB整合性とスキーマを検証します。暗号化後は最後の認証チャンクまで読み戻し、manifestと全ファイルのサイズ・SHA-256を確認してから、完成名で原子的に公開します。公開には同一ディレクトリ内のハードリンクを使うため、ハードリンク非対応の保存先では失敗します。

読み戻し専用の一時的なage鍵をメモリ内で生成し、その公開鍵も暗号化先に加えます。秘密鍵は保存しません。保管した復旧秘密鍵を使う独立復元の代わりにはならないため、定期的に隔離環境で復元も確認してください。

出力JSONの `backup_id` と `consistency_boundary` が照合用IDと復旧可能地点です。スキーマv8の `local_maintenance` と監査に開始・成功・失敗を記録します。中断した処理は次回起動時にunknownへ変え、自動で成功扱いや再実行をしません。アーカイブのDBには境界時点の開始記録が入るため、復元先ではそのバックアップ処理もunknownになります。

日次と更新前・重要設定変更前に取得し、本体と別の障害領域に直近7世代以上を保管します。自動スケジューラはありません。

## 復元

同じ版のバイナリを用意し、ネットワークを隔離してControl Planeを停止します。既存環境へ戻す場合は、その環境の暗号化バックアップも事前に取得してください。

```sh
./amuos-controlplane --db /var/lib/amuos/amuos.db \
  --restore-from /protected-backups/amuos-2026-11-05.age \
  --recovery-key-file /protected-offline/amuos-recovery.key
```

空の0700一時ディレクトリへ復号し、暗号認証、版、必須ファイル、サイズ、ハッシュ、SQLite整合性・外部キー・正確なスキーマを確認します。アーカイブのパスを展開先として使わず、絶対パス、`..`、リンク、重複、未許可ファイル、未知のフィールド・鍵束を拒否します。DB10GiB、設定・鍵束各1MiB、manifest64KiB、暗号化アーカイブ全体12GiBが上限です。大きなDBはストリーム処理し、全量をメモリに保持しません。

検証が終わるまでは現在のDBを開きません。検証後、一時DB内で全セッション・初回設定資格情報を削除し、未使用招待を取り消し、認可版を更新します。これらと復元の監査を同じトランザクションで確定してから、SQLiteバックアップAPIのトランザクションでDBを切り替えます。適用が途中で中断された場合はSQLiteの回復処理が未確定トランザクションを戻します。コミット済みなら、資格情報を無効化した復元状態が残ります。

既存DBがある場合は、切替前の整合性スナップショットを同じ状態領域の0700 `.pre-restore-*` ディレクトリへ0600で退避します。出力JSONの `retained_database` で場所を確認できます。自動削除はしません。退避DBには旧資格情報や過去の監査があるため、保護し、ログを無検証で混合しないでください。通常の切戻しは事前に取得した暗号化バックアップと、その版のバイナリで行います。

出力JSONの `config` を確認し、TLS証明書を用意して隔離状態で起動します。Ownerのパスワードで新規ログインし、必要に応じて再認証して、ユーザー有効性・グループ・割当・ホスト・監査を確認してからアクセスを戻します。バックアップ境界以降の変更・監査は回復できず、その欠落期間を `restore.complete` に記録します。管理対象ホストのサービスに停止・変更命令は送りません。

## 中断・容量不足と検証状況

完了・失敗時には一時DBを清掃します。プロセスの強制終了で残った、専用マーカー付きの一時ディレクトリは、次回に排他ロックを取得した通常起動・バックアップ・復元時に清掃します。許可外ファイルが混ざっている場合は削除せず停止します。暗号化出力の `.amuos-backup-*` 一時ファイルは強制終了時に残る場合がありますが、完成名へ自動公開しません。処理停止と保存先を確認した担当者が除去します。

CLIは15分で打ち切ります。DBスナップショット・退避・検証に空き容量が必要です。書込みエラー、誤鍵、改ざん、途中切断、欠落・重複・不正エントリ、版違い、旧資格情報の拒否、部分的なSQLite適用のロールバックを自動試験に含めています。Ubuntuで取得したバックアップを、AmuOSを動かしたことのないDebianのコンテナへ復元できることを自動テスト（CI）で確認しています。v0.5では専用32MiB tmpfsの容量不足後も既存DBを保ち、空きを戻すと再復元できることと、10ホスト・2,400サンプル・100タスクの独立復元を確認しました。条件は `docs/FOUNDATION_GATE.md` を参照してください。実ディスクの容量枯渇、電源断、実機のUbuntu Server・Debianでの独立した環境での復元、403,200件の全保持量での暗号化バックアップ・復元性能は未検証です。

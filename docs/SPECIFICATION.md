## 1. プロジェクト概要

### 1.1 目的

既存のLinux OSにインストールし、Webブラウザからサーバーやアプリケーションを統合管理できる、オープンソースのサーバー管理プラットフォームを開発する。

Proxmox VE、Cockpit、Grafana、Portainer、FileBrowserなどのOSSを参考にするが、各ソフトウェアを単純に組み合わせるのではなく、独自の統一された管理環境を提供する。

### 1.2 基本理念

**複雑なインフラ管理を、穏やかで確かなものに。**

重視する価値：

1. **安定性**：長期間、安定して稼働できること
2. **信頼性**：安心してサーバー管理を任せられること
3. **使いやすさ**：複雑な操作を直感的に行えること
4. **安全性**：不正操作や誤操作による被害を最小限にすること
5. **拡張性**：小規模環境から複数ホスト環境まで対応できること
6. **保守性**：継続的に更新・改善できる構造であること

機能の豊富さよりも、安定性・セキュリティ・操作性を優先する。

### 1.3 対応環境

初期対象：

- Ubuntu Server LTS
- Debian Stable
- Linux amd64

v0.4からの基盤対応（ADR-024）：

- Windows amd64（Control PlaneとAgent）。WSLや仮想マシンを使えない環境でも試せるようにする。Windowsサービスとしての常駐、Agentの監視値・ホスト情報のWindowsでの取得、鍵・状態ファイルの保護（NTFSのアクセス制御）、導入・更新・切り戻し・アンインストールの手順を対象とし、設計と制約はADR-024およびINSTALL-WINDOWS.mdに定める。systemd状態の取得など、Linuxにしかない機能はWindowsでは「対応していない」と表示し、0や空の値で代用しない

将来的に対応を検討：

- Linux arm64
- その他のLinuxディストリビューション
- 専用インストールISO

既存のOSを再インストールせずに導入できる方式を基本とする。

### 1.4 初期リリース（v1.0）の範囲

v1.0では、ホストの登録からファイル配置、実行環境の設定、デプロイ、起動・停止、ログ・監視、更新・切り戻しまでを、一つのURL・認証・権限・監査・タスクの仕組みで扱えることを目指す。各機能の一覧画面だけがある状態や、基盤版だけの検証完了を製品全体の完成と扱わない。

Windows上のControl PlaneからもLinux Agentのデプロイ・コンテナ・VM管理を利用できるようにする。Windows Agentは既存の監視に加えファイル管理を対象とする。Linux専用のsystemd・Docker/Compose・仮想化Adapterを、Windowsのローカルワークロード機能として対応済みと扱わない。OS・ランタイム・エンジンごとの具体的な対応表と必要権限を各段階のADRで確定し、未対応の組合せはUI/API/Agentで拒否する。

Proxmoxなどの追加Adapter、すべての言語の専用ランタイム管理、クラスタ/HA、カスタムロール、高度なダッシュボード編集、Webからのオンライン復元や自動運用は、基本範囲を満たした後の拡張とする。任意の高権限シェルを機能の代用として公開しない。

基盤版のタスクを変更操作へ拡張する前に、権限分離・監査・冪等性・中断後の照合・復旧を設計する。実装は16の順序で段階的に進め、未実装の操作は公開しない。

### 2.2 Control Plane

システム全体を統括する中央管理コンポーネント。

主な役割：

- Web UIの配信
- API提供
- ユーザー認証
- アクセス権限管理
- ホスト情報管理
- タスク実行指示
- 監視データ保存
- ダッシュボード管理
- 監査ログ保存

初期段階ではモジュラーモノリスとして実装し、不要なマイクロサービス化は避ける。

### 2.3 Agent

管理対象ホストにインストールするGo製の軽量プログラム。

主な役割：

- Linuxのシステム情報取得
- 監視データ収集
- systemdサービス管理
- Docker管理
- ファイル操作
- アプリケーション管理
- 仮想化エンジンとの連携

AgentはControl Planeに外向き接続する方式を基本とする。

各Agentは個別に認証し、通信はTLSで保護する。

通常の情報収集と高権限操作を分離し、必要最小限の権限で動作させる。

### 2.4 単一ホスト・複数ホスト

単一ホストの場合は、Control PlaneとAgentを同じLinux上に配置する。

複数ホストの場合は、各ホストへAgentを追加する。

管理対象のホスト数が増えても、利用するWeb管理画面は一つとする。

### 2.5 Agentの信頼管理

#### 初回登録

- 登録権限を持つユーザーが、登録先のホストIDと発行者の許可範囲に結び付く登録要求を作成する。Agentの自己申告でホストID・範囲を変更できない。
- 登録トークンは暗号学的乱数で生成し、平文は発行時に一度だけ表示する。DBには検証用ハッシュ、登録要求ID、発行者、対象ホスト、有効期限、消費・失効状態を保存する。トークンをURL、ログ、監査イベントに含めない。
- 有効期間は既定10分、設定可能範囲は1〜30分とし、期限判定はControl Planeの時刻を基準とする。失効・期限切れ・使用済みは拒否する。再発行時は旧トークンを失効させる。
- Agentは登録前にControl PlaneのTLS証明書と接続先名を検証する。信頼アンカーは安全な導入経路で配布し、検証無効化や未検証証明書の自動受容を認めない。
- Agentはローカルで秘密鍵を生成し、公開鍵と鍵の所持証明を送る。サーバーはトークンの消費と公開鍵・Agent ID・ホストIDの結び付けを原子的に確定し、並行登録でも一件だけ成立させる。
- 発行途中の障害に備え、消費済み登録要求に同じ公開鍵の所持証明で照会できる受付結果を永続化する。照会は既存登録結果の再取得に限定し、トークンの再使用による別鍵・別ホストの登録を許可しない。回復不能なら管理者が失効させて新規登録する。

#### 相互認証と資格情報

- 登録後の通信はmTLSを必須とする。Control PlaneはAgent証明書を検証し、AgentはControl Planeの証明書・接続先名を検証する。証明書の署名検証だけでなく、有効期間、用途、対応するAgent ID・ホストID、現在の登録状態を照合する。
- Agent資格情報の既定有効期間は30日、残り10日から自動更新する。更新には有効かつ未失効の既存資格情報と新しい秘密鍵の所持証明を必要とする。期限切れ後は自動更新せず、新規登録手順で回復する。
- 更新時は新旧資格情報の識別子を記録する。新資格情報の利用確認後に旧資格情報を失効し、移行猶予は最大24時間とする。更新失敗時は期限内でバックオフして再試行し、期限接近・失効を管理画面で通知する。
- 秘密鍵はAgent外に送らず、専用ユーザーのみ読み取り可能なファイルとして保存する。Control Planeの署名鍵とAgentの秘密鍵を分離する。CA更新では新しい信頼アンカーを認証済み経路で事前配布し、未更新Agentを識別してから旧アンカーを除去する。侵害時は通常の猶予を適用せず、対象失効・安全な再登録を行う。

#### 失効・ホスト削除

- 管理状態を `pending → active → revoked / deleted` とし、失効・削除は終端状態とする。再登録には新しいAgent IDと資格情報を発行し、旧資格情報を復活させない。
- 失効・削除を永続化してから成功を返す。未使用登録トークンと当該Agentの全資格情報を無効化し、既存接続を切断する。すべての接続・要求・データ受入時に現在の信頼状態を確認するため、接続済みでも失効後の要求を拒否する。
- データ受入と信頼状態の照合は同じトランザクション境界で行い、失効確定後に古い認証キャッシュによる書込みを確定しない。登録結果の再取得にも失効・削除の確認を適用する。
- 削除済みIDの拒否記録と失効記録は資格情報が再利用できる期間以上保持する。監視履歴・監査ログはそれぞれの保持方針に従い、ホスト削除と同時に監査証跡を消さない。
- 信頼状態を照合できない場合は要求を受け入れない。Agent切断中の失効もControl Planeに保存し、再接続時に拒否する。ホスト名・IPが一致しても信頼を引き継がない。
- 発行、登録成功・拒否、更新、失効、削除、再登録を監査する。復元で古い信頼状態が戻る問題は14.5の再登録方針で処理する。

### 2.6 タスク実行と障害時の扱い

#### 永続化する情報と状態

Control PlaneはタスクID、要求者、操作種別、対象リソース、検証済み入力の参照、冪等キー、入力ハッシュ、状態、試行ID、作成・開始・終了時刻、受付期限・実行期限、結果・エラーを永続化する。機密入力そのものは状態表示・ログに含めない。

| 状態 | 意味・遷移 |
|---|---|
| queued | 受付済み・未配送。認可・対象の信頼状態を再確認しdispatchingへ。期限切れはtimed_out、配送前取消はcancelled |
| dispatching | 配送を永続記録済み。Agentの受付確認でrunning、明示拒否でfailed。応答喪失・再起動時はunknownとして照合 |
| running | 実行受付済み。結果確認でsucceeded / failed。取消・期限到達後も停止を確認できなければunknown |
| succeeded / failed | 成功または失敗を確認した終端状態。失敗理由と副作用の有無を記録 |
| timed_out / cancelled | 未実行または実行停止を確認した終端状態。停止確認ができない場合はこの状態に確定しない |
| unknown | 実行有無・結果が未確定。再接続で照会し、証拠に基づいてrunningまたは終端状態に確定。推測で成功・失敗にしない |

- 通信断はタスク失敗を意味しない。AgentはタスクID・試行IDと受付・実行結果をローカルに永続化し、同一配送の再送には既存状態を返す。Control Plane再起動後は未確定タスクを読み込み、Agentの記録と照合する。
- 冪等キーは要求者・操作・対象と組み合わせて一意とし、同じキー・同じ入力には同じタスクを返す。同じキーで異なる入力は競合として拒否する。Agentも同じタスクIDで異なる入力を拒否する。
- タスク・重複排除記録の既定保持期間は終端後30日とする。unknownは解決まで削除しない。AgentはControl Planeの結果受領確認前に記録を削除しない。受付期限切れの古い配送は記録の有無によらず拒否する。再実行時は新規タスクとし、旧タスクへの参照を残す。
- 操作ごとに受付期限・実行期限を必須定義する。初期の読み取りタスクは受付60秒・実行30秒、バックアップは受付60秒・実行15分を既定とし、変更は上限を含む設定として記録する。期限延長を暗黙に行わない。
- Agentの再接続は上限60秒の指数バックオフとジッターを使用する。再接続時は結果照会を優先し、未確認操作を新規実行しない。期限内の同一配送再送は永続的な重複排除を前提とする。
- 読み取り専用タスクのみ、旧試行の結果を照合した上で回数制限付きの新試行を許可する。副作用を持つ処理の結果がunknownの場合は自動再実行しない。対象状態を確認して既存結果を確定するか、権限を持つ操作者が確認根拠を監査記録した上で別タスクを発行する。
- 配送前にユーザーの有効性・現在の権限・対象の信頼状態を再確認する。取消はベストエフォートとし、権限剥奪やAgent失効で既に発生した副作用まで取り消せるとは扱わない。
- 任意コードの「厳密に一回」の実行は保証しない。バックアップはタスクIDに対応する一時出力から検証後に原子的に公開し、不完全出力を成功成果物として扱わない。将来の変更操作は、重複排除・状態照合・補償方法の設計が完了するまで許可しない。
- 初期リリースでは閲覧可能な対象のタスク状態・結果を表示する。監査イベントとタスクIDを関連付け、受付・拒否・状態変化・手動解決を追跡できるようにする。

## 5. 監視機能

### 5.1 基本方針

**Grafanaを標準依存にしない。**

基本的な監視機能は独自に実装する。

監視情報はGo AgentがLinuxから直接取得する。

Control Planeがデータを保存・集計し、独自Web UIでグラフ表示する。

### 5.2 監視項目

- CPU使用率
- CPU負荷
- メモリ使用率
- Swap使用率
- ディスク使用率
- Disk I/O
- Network I/O
- 稼働時間
- ホスト接続状態
- ワークロード別リソース使用率

基盤版ではワークロード別リソース使用率を除くホスト単位の項目を対象とし、v1.0では対応するアプリケーション・コンテナ・VMの状態とリソース表示へ拡張する。Disk / Network I/Oは累積値と観測間隔に基づく増分として扱い、再起動・カウンターリセット・欠測を検出する。基盤版ではサービスの起動・停止などの変更操作は提供しない。v1.0の変更操作は8と16の権限分離と復旧条件を満たした範囲で提供する。

### 5.3 履歴保存

初期段階ではSQLiteを使用する。

保存する監視データには保持期間を設け、長期間のデータは集約する。

初期値は収集間隔15秒、生データ7日、5分単位の集約データ30日とする。集約には件数・最小・最大・平均を保持し、欠測区間を補完して正常値に見せない。保持期間・収集間隔は設定とバックアップの対象とする。削除前に集約の完了を確認する。

Agent ID・起動識別子・サンプル連番で重複を排除し、収集時刻と受信時刻を区別する。Agentの未送信データは最大10分かつ10MiBの範囲で保持し、超過分は古いものから破棄して欠測として記録する。再接続時の送信は現在の信頼状態を検証し、期限切れデータや不正な時刻・型・サイズを拒否する。最終受信から60秒以上経過したホストは切断扱いとし、古い値を現在値として表示しない。

将来的に監視対象が増えた場合、時系列データベースなどへの移行を検討する。

### 5.4 Grafanaの位置づけ

Grafanaは必須コンポーネントにしない。

必要に応じて、将来的に外部監視サービスとの連携機能を提供する。

### 10.2 リソース単位の権限制御

アカウントごとに以下を制限できるようにする。

- 閲覧可能なホスト
- 閲覧可能なコンテナ・VM
- 管理可能なアプリケーション

**権限のない操作はBackend側で必ず拒否する。**

Frontendでボタンを隠すだけの権限制御は禁止する。

デフォルト拒否を原則とする。

### 10.3 割当モデルと権限の合成

- 権限割当は `(主体、ロール、リソース範囲)` とする。主体はユーザーまたはグループとし、基盤版の範囲は全体または明示したホストID集合とする。v1.0へ向けて許可ディレクトリ・アプリ・コンテナ・VMの範囲へ拡張する際は、親ホストの権限と個別の操作・範囲を照合する契約を各機能のADRで固定する。グループはユーザーの集合とし、グループの入れ子は許可しない。
- ロールは操作権限の集合であり、グループ自体に権限を持たせるのではなく割当を通じて付与する。ユーザー直接割当と所属グループの有効な割当を和集合で合成する。ロールの名称順位による暗黙の継承は行わず、10.4の権限集合を使用する。
- 操作と範囲が一つの割当内で同時に一致した場合のみ許可する。例えば「ホストAのAdmin」と「ホストBのViewer」の組合せからホストBの管理権限は得られない。
- ホスト集合は登録済みの不変IDで管理する。新規ホストは明示追加するまで集合に含めない。全体範囲は将来追加するホストにも適用されるため、割当時にその意味を表示する。
- ホストに属するメトリクス・systemd情報・タスク結果は親ホストの範囲を引き継ぐ。ユーザー・グループ・全体設定などの全体リソースは全体範囲の対応権限を必要とする。個人設定・自分のパスワード変更は本人確認に基づく別の権限として扱う。
- 初期リリースに明示的deny割当は設けない。該当する許可がなければ拒否する。ユーザー無効化、セッション失効、Agent失効、Owner専用制約は和集合の結果に優先し、常に拒否できる制約とする。
- APIの一覧・件数・検索・履歴・リアルタイム配信にも同じ範囲を適用する。リクエストに含むIDを信用せず、対象を取得して認可し、範囲外の情報の存在や値を応答・エラーから漏らさない。
- 割当・所属・有効性の変更は認可バージョンを更新し、次のAPI要求・タスク配送・配信イベントから反映する。古いキャッシュやログイン時のロールだけで許可しない。既存の配信接続も権限を再検証して停止・再購読させる。

### 10.4 初期ロールの操作範囲

以下は基盤版の操作集合である。ファイル・アプリ・コンテナ・VMの変更権限を、既存の閲覧/collect権限から暗黙に導出しない。追加する操作ごとのOwner/Admin/Operator/Viewerの許可範囲、秘密値の利用と閲覧、危険操作の再認証/確認は、実装前にADRとAPI_AUTHORIZATION.csvへ明記する。

| 操作 | Owner | Admin | Operator | Viewer |
|---|---|---|---|---|
| ホスト・監視・読み取り専用systemd・対象タスクの閲覧 | 全体 | 割当範囲 | 割当範囲 | 割当範囲 |
| 許可された読み取り収集タスクの再要求・配送前取消 | 全体 | 割当範囲 | 割当範囲 | 不可 |
| Agent登録トークン発行・取消、Agent失効、ホスト削除 | 全体 | 割当範囲 | 不可 | 不可 |
| 非Ownerの招待・無効化、グループ・固定ロール割当管理 | 可 | 全体範囲でのみ可、下記制約あり | 不可 | 不可 |
| 監査ログ閲覧 | 全体 | 割当範囲。認証・ユーザー管理など全体イベントは全体範囲のみ | 不可 | 不可 |
| 監視保持期間など通常の全体設定 | 可 | 全体範囲のみ可 | 不可 | 不可 |
| 管理基盤のバックアップ・復元、信頼・鍵管理 | 可 | 不可 | 不可 | 不可 |

ホスト範囲のAdminによる登録は、その範囲に事前確保されたpendingホストのみを対象とする。新規ホストIDの確保・全体範囲への追加は全体AdminまたはOwnerが行う。

全体Adminが付与できるのは非Ownerロールのうち、自分の有効な操作・範囲の部分集合だけとする。Ownerのユーザー状態・所属・割当を変更できず、Owner権限をグループ経由でも付与できない。各割当変更で変更後の実効権限を検証し、管理権限経由の昇格を防ぐ。

### 10.5 Owner専用操作と認証の制約

- Ownerは有効なユーザーへの直接・全体割当のみとし、グループ経由やホスト範囲付きのOwner割当は禁止する。Owner追加・解除・移譲と、Ownerアカウントの無効化はOwner専用とする。
- 最後の有効なOwnerの解除・無効化をトランザクション内で拒否する。初回セットアップは未初期化時のみ、ローカルで生成した期限付きセットアップ資格情報で一度だけ実行可能とする。
- バックアップの作成・取得、復元、暗号鍵・CA・信頼アンカーの変更、認証の全体方針変更、復旧時のOwner回復はOwner専用操作とする。ローカル復旧はOS管理権限と復旧鍵を必要とし、通常APIの認可を迂回する公開エンドポイントを設けない。
- Owner専用の機密操作は直近5分以内の再認証を要求する。復元時のローカル手順はWeb再認証の代わりにOS管理権限・復旧鍵で実施し、回復したOwnerが再認証して運用を再開する。
- パスワードは実績のある方式でソルト付きハッシュとして保存する。招待は期限付き一回限りとし、招待時に許可されたロール・範囲を受諾者が変更できない。招待・パスワード・トークンをログに含めない。
- セッションはサーバー側で管理し、CookieにSecure・HttpOnly・SameSite属性を付ける。状態変更要求にはCSRF対策を適用する。アイドル期限30分・絶対期限12時間を既定とし、ログアウト・ユーザー無効化・パスワード変更時に対象セッションを失効する。認証失敗のレート制限と監査を必須とする。
- API・Agentから任意のロールや権限を自己申告できない。カスタムロールの作成・編集は後続機能とし、初期リリースでは固定ロールの割当管理を提供する。

- イベントID、UTC発生時刻、主体ID・種別、操作、対象ID・範囲、結果・理由コード、リクエストID・タスクID、秘密値を除く変更前後の要約を保存する。Agent自己申告の時刻とサーバー記録時刻を区別する。
- パスワード、登録・招待トークン、セッションID、秘密鍵、復旧鍵、機密入力を記録しない。エラー詳細にも同じマスキングを適用する。
- 権限変更・登録・失効などDB内の重要な状態更新と対応イベントは同じトランザクションで確定する。外部処理は受付イベントを永続化してから実行し、結果イベントを追記する。監査を書けない場合、重要な変更操作は失敗させる。読み取り収集まで一律停止させず、監査保存障害を可視化する。
- 通常APIから監査レコードの変更・個別削除は許可しない。既定保持期間は180日とし、保持期間変更はOwner専用・監査対象とする。保管期限による削除は専用処理で行い、その実施範囲を記録する。
- DBやOSを管理できる者に対する完全な改ざん耐性は初期リリースの保証範囲外とする。ファイル権限・バックアップで保護し、復元でログが巻き戻る区間は欠落期間として明示する。

Goの単一バイナリ配布を基本とし、可能な範囲でインストールを簡単にする。

### 14.4 管理基盤のバックアップ

バックアップ・復元は基盤版からの必須機能とする。本節の対象は管理基盤であり、管理対象ホストのOS全体やVM・アプリケーションデータを含むとは扱わない。v1.0では各データの保護対象・保存先・復元手段を別に定め、16.2で統合復旧を検証する。

| 対象 | 保護と保存方法 |
|---|---|
| SQLite | ユーザー・RBAC、ホスト登録・失効、タスク・冪等記録、監視履歴、監査ログ、スキーマ・マイグレーション履歴を一貫したスナップショットに含める |
| 設定 | 配布版、設定形式版、監視・保持設定、接続先・信頼設定を記録。ホスト依存のパス・アドレスは復元時に再確認 |
| シークレット | 保存済み機密値とその暗号化メタデータを暗号化アーカイブに格納。平文の設定・一時ファイル・ログへの出力を防ぐ |
| 暗号鍵 | データ暗号鍵・署名鍵など復元に必要な鍵を、復旧鍵で暗号化した鍵束として保存。Agentの秘密鍵は対象外 |
| マニフェスト | バックアップID、作成時刻、一貫性境界、製品・DB・設定形式版、対象一覧、件数、鍵ID、完全性検証情報を含める |

- 手動バックアップはローカルのOwner管理手順で実行可能とする。OS管理権限を必要とし、作成・成功・失敗を監査する。Web/APIを後から提供する場合も10.5のOwner制約を適用する。
- SQLiteの稼働中DBファイルだけを単純コピーしない。初期方式ではバックアップ用保守モードで新規変更・タスク配送・監視書込みを一時停止し、実行中タスクを完了待ちまたは未確定状態として永続化する。その後、SQLiteのバックアップAPIでスナップショットを作成し、同じ境界で設定・シークレット・鍵束を採取する。
- 保守中の受信は一時受付不可として通知し、Agent側の有界バッファで扱う。監査記録を含むスナップショットの境界をマニフェストに記録する。設定・鍵更新との同時実行を排他し、取得完了後に保守モードを解除する。
- 一貫性境界の確定前に既存書込みを完了させ、それ以降の書込みはスナップショットと関連ファイルの採取完了まで待機または拒否する。失敗時も保守モードを解除し、プロセス停止で残ったバックアップは再起動時にunknownとして検証・清掃する。未検証アーカイブを自動公開しない。
- アーカイブは認証付き暗号化で機密性と完全性を保護する。暗号方式は実績のあるライブラリから選定し、独自暗号を設計しない。復旧鍵は同じアーカイブや同じ保存先に平文で置かず、独立した安全な保管先に保存する。鍵IDで対応を確認し、復旧鍵紛失時は復元できないことを手順に明示する。
- 一時領域は専用ユーザーだけがアクセスできる権限とし、失敗・完了時に一時ファイルを除去する。バックアップの完全性検証とDB整合性検査を通過してから完成名で公開する。ディスク不足・中断・暗号化失敗時は不完全な成果物を成功扱いしない。
- バックアップは本体とは別の障害領域にも保管する。初期運用では日次の手動取得と更新前・重要設定変更前の取得を手順化し、直近7世代以上を維持する。自動スケジューラは将来拡張のままとする。最新の検証済み取得時刻を復旧可能地点として表示・記録し、実施しなかった期間の復旧を保証しない。

### 14.5 復元と信頼の再確立

1. 利用者アクセスとAgent接続を遮断し、Control Planeを停止する。復元先は隔離環境を基本とし、元のControl Planeと同じ識別情報で並行稼働させない。現状のDB・設定は上書き前に退避する。
2. OS管理権限・復旧鍵を持つ復旧担当者がアーカイブを検証し、対象一覧、暗号認証、鍵ID、製品・スキーマ互換性を確認する。初期リリースは同じ製品版への復元を保証対象とし、未対応の版・破損・鍵不一致は既存環境を変更する前に拒否する。
3. 空の一時復元先にDB・設定・シークレット・鍵束を展開し、SQLite整合性、必要ファイル、鍵での復号、ファイル権限を確認する。検証後に一式を切り替え、一部だけが新旧混在する状態で起動しない。失敗時は停止状態で退避一式へ戻す。
4. 通常通信を再開する前に全セッション、未使用招待・登録トークン、復元されたAgent資格情報を無効化する。復元後に新しいAgent認証CAを発行し、旧CAをAgent認証の信頼対象から外す。これにより、取得後に失効した資格情報・削除したホストが古いDBから復活しても接続できない。Agentは安全な経路で新規登録する。
5. 元の署名鍵は通常認証に再使用しない。復元したデータ暗号鍵は既存秘密値の復号にのみ必要な範囲で利用し、新しい鍵へ再暗号化する。取得後に変更された外部シークレットは復元後に確認・再設定する。侵害疑いのある鍵・秘密値は再使用しない。
6. 復元された未完了タスクはqueuedを含めunknownとして保留し、自動配送・再実行を止める。復元された認可が古い可能性を前提に、回復したOwnerがユーザー有効性・グループ・割当・外部で実施済みの操作を照合する。必要なら非Ownerを一時無効化し、承認後に個別に再開する。
7. 復元元ID・取得時刻・復元担当・検証結果・欠落する期間を新規監査イベントとして記録する。バックアップ取得後のログはアーカイブから回復できないため、退避環境のログは別の証跡として保持し、検証なく時系列を混合しない。
8. Ownerの再認証、認可確認、再登録したAgentの監視確認、主要画面の確認を通過してから利用者・Agent通信を再開する。復元により管理対象ホスト上のサービスを停止・変更しない。

### 14.6 導入・更新・復元の検証記録

- 初期リリースで対応するUbuntu Server LTS・Debian Stableの具体的な版、バイナリ版、前提パッケージ、TLS・時刻同期・ネットワーク要件、必要ディレクトリと権限、systemd設定、Owner初期化、Agent登録・失効、アンインストール時のデータ保持を手順に記載する。対応版の確定はPhase 0の完了条件とする。
- クリーンな環境で、文書のみを使った導入と再起動後の復帰を検証する。更新は初期リリースでは手動でよいが、対応する更新元、互換性検査、更新前バックアップ、失敗時の同版復元を文書化する。DB移行後に旧バイナリだけへ戻す手順は禁止する。
- 復元テストはリリース候補ごと、およびバックアップ形式・スキーマ・鍵管理変更ごとに、既存状態を引き継がない空の環境でCIから行う。コンテナ/VM/別の状態ディレクトリ等を使い、バックアップ元のファイルやプロセスに暗黙に依存しないことを確認する。破損、誤った復旧鍵、必要ファイル欠落、容量不足、途中停止、非互換版を含める。
- テスト用シークレットの復号、ユーザー・範囲付きRBAC・監視履歴・監査ログ・タスク記録の一致、旧セッション・旧Agentの拒否、再登録後の収集再開を検証する。データ量、件数、版、所要時間、失われる区間と手動確認を記録する。
- 負荷検証の基準構成は「10ホスト・同時5ユーザー・15秒収集・5.3の保持量」とし、CIでの試験条件、操作回数・データ量・実行時間・資源使用量を明記する。24時間の経過だけを合格条件にせず、主要操作の反復、通信断/再起動、蓄積と保持処理、負荷に対するメモリ/保存容量の推移を検証する。保持期限・集約・時計境界はテスト用の時計や事前データでも検証し、実時間での長時間運転と混同しない。バックアップ15分以内、同じ試験データ量で復元から監視再開まで60分以内という復旧目標は維持する。復旧鍵と対象ホストが利用可能な条件を明記し、未達は原因と改善を記録する。

上記は設計上の目標であり、実測済みの性能値ではない。CIの反復/負荷試験では予期しないプロセス停止、未説明の欠測、権限外のデータ受入、保持処理後も増加し続ける保存量がないことを確認する。障害注入で生じた欠測・中断は正常運転と分けて記録する。長時間運転・手動実機試験は変更や不具合の性質に応じて追加する補助検証とし、全リリースの一律必須条件にはしない。

|---|---|
| 正常系 | 許可ディレクトリの一覧・情報・ダウンロード・アップロード・作成・テキスト編集・名前変更・移動・削除がUI/API/Agentで成立 |
| 異常系 | パストラバーサル、symlink/reparse point、検査後の差替え、競合編集、途中切断、容量不足を検証。不完全なアップロードを完成ファイルとして公開しない |
| 認可 | ホスト・ディレクトリ・操作別RBACとOS権限の両方を検証。Agent資格情報/状態/管理基盤DB/秘密鍵の領域を公開しない |
| 復旧 | 両プロセス再起動・転送中断・書込み途中停止後の状態を照合。上書き/削除の確認・退避/回復の範囲を文書化し、監査にファイル内容を残さない |

### Phase 4：実行環境・デプロイ・コンテナ（v0.7〜v0.8）

開始条件はファイル管理の基本操作と、ワークロード別権限・シークレット保護・高権限Adapter・副作用を持つタスクの設計レビュー完了とする。

- v0.7：LinuxのManaged Service。アプリ登録、Python/Node.jsやビルド済み実行ファイルの実行設定、Git/アップロードからのデプロイ、依存関係・環境変数/秘密値、起動・停止・再起動、自動起動/再起動、ログ・リソース監視、版の更新/切戻し。
- v0.8：Linux Docker/Compose。コンテナ・イメージ・ボリューム、ポート・設定・秘密値、作成/起動制御/削除、Composeのデプロイ・更新/切戻し、ログ・監視を共通の画面・権限・タスクへ統合。

| 分類 | 合格基準 |
|---|---|
| 正常系 | 宣言したランタイムとエンジンで、ファイル配置から実行環境設定・デプロイ・起動・ログ/監視・更新/切戻しまでを画面だけで完了できる |
| 異常系 | エンジン/ランタイム未導入、不正構成、ビルド/依存取得失敗、ポート競合、ヘルスチェック失敗、途中停止、タイムアウト、重複配送を検証。unknownの変更操作を自動再実行しない |
| 認可 | ホスト/アプリ/コンテナ範囲、秘密値の登録・使用・閲覧を個別に検証。Dockerソケットや任意の高権限シェルを直接公開しない |
| 復旧 | Control Plane/Agentの停止・更新が稼働中ワークロードを不用意に停止しない。旧版と実状態を保持し、デプロイ失敗の切戻しとタスク照合を再現。基盤設定の復元とアプリデータ/ボリュームの保護を分けて検証 |

### Phase 5：基本VM管理（v0.9）

一つの仮想化Adapterと対応版をADRで決め、9.2のVM基本操作・コンソール・スナップショット・バックアップ/復元を提供する。Proxmox等の追加Adapterの完成を必須にしない。

| 分類 | 合格基準 |
|---|---|
| 正常系 | 対応エンジンのVM作成から資源/ストレージ/ネットワーク設定、起動制御、状態/監視、コンソール、スナップショットとバックアップ/復元を再現 |
| 異常系 | 仮想化未対応、エンジン未導入、資源不足、外部API障害、操作中断、重複配送で不正な成功や破壊的な再実行を防ぐ |
| 認可 | ホスト/VM範囲と作成/削除/コンソール/スナップショット/復元の権限を分け、範囲外アクセスをUI/API/Adapterで拒否 |
| 復旧 | 再接続時にVMの実状態と操作記録を照合。管理基盤の再起動でVMを停止しない。VMデータのバックアップ復元と管理基盤の復元を別々に検証 |

### Phase 6：統合運用・v1.0の出荷検証

新しい機能を個別に増やす段階を終え、16.2の一連の運用を検証する。UIの操作・対象選択・エラー/タスク/監査の表現、対応表と手順を統一し、追加機能を含むCIの反復操作・負荷・障害・更新・復旧を再実施する。16.1の基盤試験成功を、追加した機能の証跡へ流用しない。インストーラーの完全自動化や新しいAdapter追加は、この検証の代わりにしない。

### 16.2 v1.0共通の出荷条件

- 1.4の基本範囲とPhase 0〜6の合格基準を満たす。ファイルの読取りだけ、デプロイの登録だけ、VMの一覧だけなどの途中状態で完了としない。対応OS/ランタイム/エンジンと未対応項目を固定し、変更には範囲と理由のレビューを必要とする。
- 管理者がホスト・許可ディレクトリ・実行環境を用意し、委任された利用者がファイルを配置/編集してアプリをデプロイし、状態・ログ・監視を確認し、更新と切戻しまで行うE2Eを実施する。Docker/ComposeとVMの基本運用も共通画面から完了できることを確認する。
- 一覧・対象選択・API直接呼出し・ダウンロード・ログ・コンソール・進捗配信を含め、別ホスト/ディレクトリ/ワークロードの情報漏れや変更がないこと、権限の取消が次の操作に反映されることを検証する。秘密値を画面・タスク結果・ログ・監査へ漏らさない。
- 作成/更新/削除など副作用を持つタスクで、通信断・CP/Agent停止・重複・監査保存失敗・容量不足を挿入する。途中結果やunknownを成功とせず、実状態を照合して安全に回復できることを確認する。
- CIを主な出荷判定とし、単体・統合・認可・主要画面E2E・静的解析、配布物の導入/更新/切戻し、クリーン環境復元、主要操作の反復と障害注入を実行する。Ubuntu Server/Debian/Windowsの対応範囲をランナー/コンテナ/VMで検証し、Windowsは実サービス・NTFS保護・ファイル管理も対象とする。仮想化等に必要ならセルフホスト型CIを用い、検証環境不在を合格と扱わない。24時間の実時間待機や別途の手動実機確認を一律の必須条件にはしない。
- 14.6の復旧目標を追加機能を含む候補版で満たす。管理基盤DB、アプリファイル/データ、Dockerボリューム、VMディスクの保護対象と復旧手段を区別し、管理基盤のバックアップだけで全データを保護できると表示しない。復元後の旧資格情報拒否とワークロードの再照合を検証する。
- 認証迂回、権限昇格、秘密値漏えい、二重実行による破壊、復元不能などの既知の重大不具合を、利用者のIssue待ちで出荷しない。実装・試験環境・負荷・期待値/実測値・証跡・制約をPROGRESS.md/TESTING.mdへ記録する。環境固有の問題は版・OS・導入方法・関連エンジン・再現手順・秘匿化したログをIssueで収集し、再現可能な修正には回帰試験を加える。脆弱性はSECURITY.mdの非公開窓口で扱う。

v1.0後も導入・復旧・認可・E2E・監査・依存関係検査を継続し、自動運用と追加Adapter・対応規模の拡張を行う。

## 18. 現時点での設計上の決定事項

### 採用する方針

- 既存Linuxにインストールする
- Go + React + Vite+を基本技術とする
- Control Plane + Agent構成
- 一つのURL・認証・UIに統合する
- マルチユーザーと細かいRBACを搭載する
- Grafanaを必須としない
- FileBrowserを必須としない
- 基本監視・ファイル管理は独自UIで提供する
- Dockerなどの実行エンジンは既存技術を活用する
- Python Botなどの直接実行にも対応する
- 既存OSSの設計・ライブラリ・APIを積極的に研究する
- 安定性・信頼性・セキュリティを優先する

- 基盤版をPhase 1・2と16.1の検証で固め、v1.0は1.4の製品機能と16.2の統合出荷条件を満たす
- Agentは期限付き一回限り登録とmTLS、資格情報の更新・失効を必須とする
- タスクは永続状態・重複排除・結果照合を持ち、結果不明の変更操作を自動再実行しない
- RBACは範囲付き割当の和集合と明示したOwner制約で評価する
- 管理基盤のバックアップ・復元、導入手順、認可・主要画面E2Eを初期リリースに含める
- 本書を仕様の基準、直下のCONTRIBUTING.mdを開発手順、その他の開発資料をdocs/配下に統一する

### 今後決定する事項

- 正式なプロジェクト名
- 具体的なAgent通信プロトコルの転送方式・メッセージ形式（mTLSと信頼管理は決定済み。Phase 0で確定）
- 高権限操作の分離方式
- 監視データの具体的スキーマ・索引（初期収集間隔・保持期間は5.3で決定済み。Phase 0で確定）
- ファイル管理の安全な実装方式
- Managed Serviceの隔離レベル
- 各機能の具体的なAdapter・OS・ランタイム対応と操作契約（v1.0の範囲は1.4、実装順序は16とPLAN.md）
- インストール・アップデートの具体的なコマンド・配布物・対応版（初期の手動手順・復旧要件は14で決定済み。再インストールなしで更新する方針と配置の分離はDECISIONS.md ADR-009。Phase 0で確定）
- 専用OS版を開発するかどうか

高権限操作の分離、ファイル管理、Managed Serviceの隔離は後続Phaseの着手前に確定する。初期リリースに必要な暗号ライブラリ・パスワードハッシュ方式、設定上限、DBスキーマ・API契約はPhase 0で本書の要件を満たす具体案に固定し、未決定のままPhase 1の実装へ進まない。

## 19. 最終的に目指すもの

本プロジェクトは、単純なProxmox VEの代替でも、GrafanaやFileBrowserを一つにまとめた管理画面でもない。

**さまざまなサーバー・アプリケーション・コンテナ・仮想マシンを、安全かつ直感的に扱える独立した統合管理プラットフォーム**を目指す。

既存OSSの実績を活かしながら、統一されたユーザー体験と、安定して運用できる管理基盤を提供する。

将来的には専用サーバーOSとしての展開も視野に入れるが、まずは既存Linux上で利用できるソフトウェアとして完成度を高める。

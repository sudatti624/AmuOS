# 設計判断

## ADR-001: 最初の実装単位

仕様v0.4 §16の順序に従い、認証・認可・監査を先に実装する。AgentとUIは未実装として扱い、ダミーのホスト監視値は提供しない。Phase 0の全体ゲートは設計資料を用意しただけで完了扱いにしない。

## ADR-002: 暗号と通信

Go 1.27系、chi v5、modernc.org/sqliteを採用。パスワードはgolang.org/x/crypto/argon2のArgon2id（メモリ64MiB、反復3、並列度2、ランダム16バイトsalt、32バイト出力）。セッションとCSRFはそれぞれ独立した32バイト乱数。DBにはSHA-256のみ保存する。比較は定数時間。パスワードは12〜128バイト、リクエスト本文は16KiB上限。生の秘密値を監査しない。

HTTPSを必須とする。テストのhttptest経路を除きHTTPで起動しない。X-Forwarded-Forや転送先Originを信頼せず、外部Originは明示設定する。ログイン失敗制限は接続元IPで評価し、メモリの上限を設ける。

## ADR-003: 初期対応環境

Linux amd64、Ubuntu Server 24.04 LTSおよびDebian 13を初期検証対象とする。Windowsは開発・単体テスト専用。配布前に両Linuxのクリーン環境で導入・停止・更新・復元を実証する必要があり、現時点では対応済みと宣言しない。

## ADR-004: ツールと未完了条件

Goは公式アーカイブのSHA-256検証後にローカル使用。正確な依存版はgo.mod/go.sumに固定する。sqlc/gooseのCI生成・移行、React/TypeScript・Vite+・Tailwind・shadcn/uiの画面基盤は後続タスク。Vite+の正式セットアップ前に別のビルド基盤を確定しない。

## ADR-005: OSSライセンスと公開形態

Apache License 2.0で https://github.com/sudatti624/AmuOS に公開する。LICENSEは正規全文を無改変で置き、依存（MIT/BSD-3-Clause）にNOTICEを要するものがないためNOTICEは作らない。Goモジュール名は公開URLに合わせる。脆弱性はGitHubの非公開報告で受け付ける。貢献はApache-2.0第5条に従い、CLA・DCOは導入しない。開発ルールはCONTRIBUTING.mdに集約する。

## ADR-006: アカウントのライフサイクル

仕様§10.5の招待を24時間・名前固定・非Ownerの固定割当として具体化する。発行時だけでなく受諾時も発行者の最新権限を確認し、権限変更後の古い招待による昇格を防ぐ。招待の平文は発行結果で一度だけ返し、配送は操作者が行う。メール送信や外部サービスは追加しない。

Ownerの状態変更は明示的な再認証を必要とする。ログインだけでは再認証済みとして扱わない。最後の有効Ownerの無効化チェックと更新は同じDBトランザクションで行う。パスワード変更とユーザー無効化は全セッションを削除し、再有効化後の復活を防ぐ。

既存DBはユーザーデータを保持してスキーマv1からv2へ移行する。再認証時刻・招待と固定割当を追加し、既存セッションの再認証状態は空とする。移行失敗は全変更をロールバックし、新しいDBを作り直して隠さない。Ownerのロール移譲とグループ/割当の編集APIは別の実装単位とする。

## ADR-007: 権限変更とOwner移譲

所属・固定割当の変更はユーザーのauthorization_versionを進め、変更対象の未使用発行招待と再認証を取り消す。初期実装は認可をキャッシュせず、要求ごとのDB照合で権限剥奪を反映する。グループOwnerは禁止し、Ownerの所属やOwnerを含むグループの変更にもOwnerの再認証を要求する。

Owner追加・解除は通常の割当置換と分離し、対象の非Owner割当を維持する。移譲では移譲元を全体Adminとし、移譲先にOwnerを直接付与する。途中の失敗で管理者不在にならないよう、両者の更新と監査を原子的に行う。Owner割当が変わったユーザーの全セッションを失効し、権限昇格前のセッションを引き継がない。移譲元のCookieも削除する。

## ADR-008: 監査の相関と保持

HTTPリクエストIDはサーバー側で生成し、応答と業務・拒否イベントを結び付ける。未検証のヘッダー、実際のURLやクエリ・本文を監査に転記せず、拒否イベントは固定ルートと理由コードに限定する。監査保存のために拒否要求のセッションを延長しない。

保持期間は既定180日、設定範囲1〜3650日とする。初期の削除は再認証済みOwnerが専用APIで明示実行する手動バッチとし、1回1000件に制限する。設定更新とその前後値、削除とその実施範囲の監査を原子的に確定する。個別イベントIDや任意の削除基準は受け付けない。自動化は後続タスクとする。

## ADR-009: 再インストールなしの更新

更新は再インストールを前提とせず、既存のデータ・設定・資格情報を保持したままバイナリを差し替えて行う。仕様§14.3・§14.6に従い、初期リリースは手動更新とし、自動更新機構は後続Phaseとする。

- 配置を役割ごとに分ける。Linuxではバイナリを `/usr/local/bin`、設定を `/etc/amuos`、DB・鍵などの状態を `/var/lib/amuos` に置き、バイナリの差し替えで設定と状態を変更しない。具体的なパスと権限は計画4のLinux導入時に確定し、OPERATIONS.mdに記載する。
- 更新手順は「停止 → 整合性のあるバックアップ取得と検証 → バイナリ差し替え → 起動時の自動スキーマ移行 → 動作確認」とする。稼働中DBの単純コピーをバックアップとして扱わない。
- スキーマ移行は前進のみ・各版を順に原子的に適用する。DBがバイナリより新しい場合は起動を拒否する（実装済み）。
- 失敗時の戻し方は「更新前バックアップの復元と旧バイナリの組」に限定する。移行後のDBに旧バイナリだけを戻す手順は提供しない。
- Agent導入後は、Control Planeを先に更新しても直前の版のAgentと通信できる互換範囲を設け、全ホストの一斉更新を要求しない。具体的な互換範囲はAgentのプロトコル設計時に決める。
- 配布物は当初tar.gzと手順書で始め、`.deb` パッケージによる `apt` での更新を後続の候補とする。具体的なコマンド・配布物・対応版は仕様の「今後決定する事項」どおりPhase 0で確定する。

## ADR-010: 監査保持の自動化

順序1の完了に向け、ADR-008の手動処理を自動化した。既定は有効、保持180日。Ownerが再認証付き設定で停止/再開する。通常1時間、残件1分、失敗5分の予定をDBに保存する。1回1000件・処理上限5秒とし、予定・削除・監査を同じトランザクションに含める。自動処理の固定主体systemは期限切れ削除だけを行い、ユーザー権限・保持設定を変更できない。

## ADR-011: ホスト台帳の永続的な冪等性

順序1の非冪等なホスト登録枠作成は、要求者・host.create・台帳範囲・キーハッシュを一意とする。認証・認可・CSRFを毎回確認してから、同一入力なら元の結果を返す。キーやリクエスト本文は平文保存しない。ホスト・操作記録・監査を原子的に確定する。結果保持30日後も拒否記録を残し、遅延した再送を新規実行しない。副作用を持つ外部タスクの実装は順序4・5で行う。

## ADR-012: 基盤設計の固定とレビュー

順序0の設計不足をFOUNDATION_CONTRACT.mdで具体化し、全27ルートの認可表をCSVと実装照合試験で管理する。バックアップは大きなDBの扱いと独自暗号形式の回避を優先し、従来の単体AES-GCMアーカイブ案からage v1・X25519へ変更する。AES-256-GCMは保存シークレットの保護に用いる。順序4で実装するまで実行可能なバックアップとは扱わない。

配布OS・配置、Agentの転送方式/認証/エラー/データ制約、タスクの状態/期限/照合、鍵保護と復元時の信頼再確立を同じ契約に固定する。レビュー結果とテスト対応はFOUNDATION_REVIEW.md。Go検証版は.go-versionの1.27.3とし、CIも同じ版を使う。順序0/1の完了と、画面・復元・実Agent・運用品質を含む製品Phaseの完了を混同しない。

## ADR-013: Web画面の構成と配信

仕様§11・§16の順序3として、React / TypeScript / Vite+ / Tailwind v4 と、shadcn/uiの方式（Radixを使う部品をリポジトリ内に置く）で画面を作る。初期リリースで提供するのは概要・ホスト・アクティビティ・ユーザーとグループ・設定と、初回設定・ログイン・招待受諾。監視とタスクはAPIがないため導線を置かない。表示は日本語、既定はダークテーマ。配色はロゴ（紫・ピンク・水色）に合わせ、グラデーションはロゴ文字・細い帯・ログイン画面の背景に限って使う。

- 配信: `web/` のビルド結果を `internal/webui/static/app` に出力し、Goのembedで単一バイナリに含める。ビルド出力はGitに含めない。未ビルドのバイナリは画面の代わりに503の案内を返す。画面のページと `/assets/` は固定パスのみ認証なしで返し、それ以外は従来どおり監査付きの404とする。
- CSP: 画面は `script-src 'self'`・`style-src 'self'` に限定する。ダイアログ部品が挿入する `<style>` だけを許可するため、`index.html` の応答ごとに新しいnonceを生成してビルド時のプレースホルダーを置き換える。`'unsafe-inline'` は使わない。APIのCSPは変更しない。
- CSRF: トークンはログイン応答でのみ返り、サーバーにはハッシュしかないため、タブ単位のsessionStorageに保持する。新しいタブや保存できない環境では再ログインを求める。XSSがあればトークンも読まれるため、CSPで防ぐ前提とする。
- 認可: 画面の表示制御は権限に合わせた見た目の調整にすぎず、すべての読み書きはAPIで認可する。E2Eで、画面で隠したAPIを直接呼んでも拒否されることを確認する。
- `GET /me` に本人のusernameを追加する。他人の情報は返さない。
- Ownerの再認証が必要な操作は、403のときにパスワード入力を求めて1回だけ再試行する。
- E2Eは実バイナリを新しいDB・自己署名証明書（`scripts/devcert`、テスト専用）で起動して行う。認証入口の回数制限を共有しないよう、テストファイルごとにサーバーを分ける。

## ADR-014: v0.1の配布と導入確認

最初の配布物はLinux amd64のtar.gzとし、バイナリ（`amuos-controlplane`）、LICENSE、導入手順、同梱する全依存のライセンス本文（THIRD_PARTY_LICENSES.md）を含める。GitHub Releasesにはプレリリースとして公開し、本番利用を推奨しない旨を明記する。

導入の確認は、CIでUbuntu 24.04ランナーとDebian 13コンテナに配布物を手順どおり導入する自動試験で行う。`v*` タグのpushでは、すべてのジョブが成功した場合だけリリースを作成する。実機のUbuntu Server・Debianでの導入とsystemdでの常駐は順序4で検証し、v1.0の証跡は独立したVMで取得する（PLAN.md「リリースの目安」）。

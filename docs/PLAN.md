順序6の基盤ゲートを通過してから、順序7以降へ進む。高権限操作のAdapter、ディレクトリ/ワークロード範囲、秘密値、副作用を持つタスクの冪等性・中断照合・回復方法は、各段階の着手前にADRとAPI/認可契約で確定する。基盤ゲートを通過しても、後から追加した機能の安全性と復旧を検証済みとは扱わない。

順序0〜5の完了は各実装範囲の完了であり、製品全体の完成とは別である。対応OS/ランタイム/エンジンの範囲は仕様§1.4に従う。Windows上のControl PlaneからLinuxのデプロイ等を管理できる構成とし、Linux専用機能をWindows Agentのローカル機能として約束しない。

## 検証の位置付け

CIを主な出荷判定にする。単体・統合・認可・E2Eに加え、実バイナリ/配布物による導入・常駐・再起動・更新/切戻し・クリーン環境復元をCIで反復する。Ubuntu Server 24.04/Debian 13/Windowsの宣言した対応範囲を検証し、負荷をかけた主要操作、通信断・中断・容量不足、保持期限や時計境界もシナリオ化する。実機で24時間待つことや、別途の手動導入試験を全リリース共通の必須条件にはしない。

仮想化など専用環境が必要な機能は、必要に応じてセルフホスト型を含むCIランナーで検証する。環境がないため未実施の試験を合格扱いせず、対応表と検証結果を記録する。長時間運転や手動の実機確認は、変更のリスクや不具合調査に応じて追加する補助検証とする。

利用者固有のOS設定・権限・ストレージ・ネットワーク等の問題は、環境情報と再現手順を付けたIssueで収集する。再現できた不具合は可能な限りCIの回帰試験に加える。認証迂回・権限昇格・データ破損・復元不能などの既知の重大不具合を、利用者の報告待ちで出荷しない。試験条件・負荷・期待値/実測値・証跡・未実施事項はTESTING.md/PROGRESS.mdへ記録する。

## v1.0より後の拡張

Proxmoxなどの追加Adapter、対応OS/ランタイムの拡大、MCP、SSO、クラスタ/HA、自動運用などは仕様§17の候補とする。ファイル管理・デプロイ・コンテナ・基本VM管理はこの後続枠へ先送りしない。

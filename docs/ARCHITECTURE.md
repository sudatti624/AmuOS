# 基盤設計

基準: SPECIFICATION.md v0.4 §2、§10、§12、§14。初期実装はControl Planeの認証・認可・監査に絞る。

## コンポーネントと境界

`cmd/controlplane` はHTTPS起動・設定・停止を担当し、`internal/controlplane` はHTTPとユースケース、`internal/store` はSQLiteとトランザクション、`internal/rbac` は副作用のない認可判定、`internal/security` はパスワード・乱数・ハッシュを担当する。SQLをハンドラに埋め込まない。

利用者ブラウザはHTTPSでのみ接続する。外部由来のユーザーID・ロール・ホストIDを権限として信用しない。CookieのトークンをDB内のハッシュに対応付け、要求ごとに有効ユーザーと最新割当を取得する。変更要求ではOriginとCSRFトークンを確認する。ログイン前にもOriginを確認する。

SQLiteは単一接続、foreign_keys、WAL、busy_timeoutを使用する。重要変更と監査は一つのトランザクションで実行。認可に使うユーザー・割当の読み込みも同じ書込みトランザクション内で実施し、認可変更との競合を直列化する。システム時刻はUTCで記録する。

## データモデル

| テーブル | 用途・制約 |
|---|---|
| users | 不変ID、正規化ログイン名一意、パスワードハッシュ、有効性 |
| groups / memberships | 非入れ子のユーザー集合、組合せ一意 |
| grants | 主体種別・ID、固定ロール、全体/明示ホスト。Ownerはユーザー直接・全体のみ |
| sessions | ランダムトークンのSHA-256、CSRFのSHA-256、開始・最終利用・絶対期限、ユーザーFK |
| invitations / invitation_grants | 名前・発行者・期限・使用/取消時刻、トークンハッシュ、発行時に固定した非Ownerロールと範囲 |
| bootstrap | 期限付き一回限りの初回設定トークンのハッシュ |
| hosts | 不変ID、表示名、pending/active/revoked/deleted |
| audit_events | 主体、操作、対象ホスト範囲、結果、理由、UTC時刻。通常APIで変更・削除不可 |

スキーマの具体形は `internal/store/migrations/` に置く。現在はgoose形式SQLを組込みのバージョン付き起動マイグレーションで適用する。sqlcの導入はクエリ契約が安定する次の段階で行う。

アカウント管理はスキーマv2で追加した。v1のユーザー・セッションを維持し、sessionsへセッション単位の再認証時刻（NULL初期値）を追加する。未適用の全移行を一つのトランザクションで行い、途中失敗時はスキーマ版も含めて戻す。

招待の発行と受諾では、要求するロールの操作集合が発行者の最新権限・範囲に含まれることを確認する。受諾時はトークン消費・ユーザー・固定割当・監査を原子的に保存する。ユーザー無効化では全セッション削除と未使用の発行招待取消も同時に行う。Ownerの無効化は再認証と有効Owner数を同じトランザクション内で検証する。

## Agent・タスク・復旧の設計契約（未実装）

AgentはHTTPS JSONの外向き短ポーリングで接続し、登録後は専用mTLSリスナーを使用する。Agent認証CAとサーバー証明書の信頼を分離する。登録は署名検証済みCSRで鍵所持を確認し、一回限りトークン消費と登録結果の保存を原子的に行う。証明書シリアルと現在のAgent状態を各受入トランザクションで検証する。

tasksは要求者・操作・対象・冪等キーの一意制約を持つ。2.6の状態遷移と試行履歴を永続化し、unknownは自動再配送しない。Agent側もSQLiteに受付と結果を保存する。監視サンプルはAgent ID・起動ID・連番を一意とする。保持値は仕様§5.3に従う。

バックアップは保守モードで書込みを止め、SQLiteバックアップAPIと同じ境界の設定・鍵を暗号化する。アーカイブは版付きマニフェスト、DB、設定、鍵束から構成し、AES-256-GCMと独立した32バイト復旧鍵を使用する。復元先で検証後に一式を切り替え、全セッション・招待・登録資格情報を失効し、Agent CAを再発行する。これらの経路はまだ提供しない。
